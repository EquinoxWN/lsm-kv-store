## Benchmarks

Command: `go test -run '^$' -bench . -benchmem -benchtime 3000x .` (100-byte values, 20-byte keys).

| Benchmark | Time per op | Throughput | Allocations |
|---|---|---|---|
| PutSync (fsync every write) | 2.34 ms | ~430 durable writes/s | 5 allocs, 351 B |
| PutNoSync | 8.4 µs | ~119,000 writes/s | 5 allocs, 351 B |
| Get (50,000 keys over memtable and L0 tables) | 15.5 µs | ~65,000 reads/s | 5 allocs, 5.7 KB |

### Reading the numbers

- Durable writes are bound by fsync latency on this disk. That is the cost of the durability
  guarantee, and it is the baseline for group commit in M3.
- Reads allocate 5.7 KB because each lookup reads a whole 4 KiB block without a block cache.
  L0 tables overlap, so a read may check several tables. Compaction (M2) and a block cache will
  change this, and these numbers are the "before".
- These are single-machine micro-benchmarks, not the YCSB comparison against sled planned for M3.

## Quality control (DMAIC)

| Phase | This repository |
|---|---|
| Define | Write-heavy storage engines must append and flush in bulk without losing a write the caller was told had succeeded; this project serves engineers who want to understand or debug engines like Cassandra and RocksDB. M1 counts when a write survives a process crash once `Put` returns, a full memtable is flushed to an SSTable with a sparse index and bloom filter, and recovery ignores torn WAL tails ([RFC 0001](../rfc/0001-design.md)); the RFC sets no numeric throughput target for M1. |
| Measure | `go test -count=1 -v ./...`, `make fuzz` and `go test -bench` (100-byte values, 20-byte keys) on an Intel Core i7-13700H with Windows 11 and an NVMe SSD, repeated with `govulncheck` in the 2026-10-06 recheck. 25 tests passed, 0 failed; 200 of 200 acknowledged writes survived a simulated crash; about 3.3 million fuzz inputs gave 0 crashes; PutSync took 2.34 ms (~430 durable writes/s), PutNoSync 8.4 µs and Get 15.5 µs. |
| Analyze | Durable writes are bound by fsync latency, one fsync per write; reads allocate 5.7 KB because each lookup reads a whole 4 KiB block with no block cache, and overlapping L0 tables may each be checked. No defects recorded. The recheck showed that single-run micro-benchmarks vary (Get 8.2 µs on another day); YCSB results against sled are not measured yet (M3). |
| Improve | No defect needed a change in M1; group commit, compaction and a block cache are planned improvements measured against this baseline. |
| Control | The `ci` workflow's `build` job runs `make ci` (gofmt, `go vet` and `make test` with the race detector) and `make audit` (`govulncheck`) on every push and pull request. In the code, every WAL record and SSTable block carries a crc32c, a checksum mismatch stops replay and a corrupt block returns `ErrCorrupt`, empty keys and oversized entries are refused, the SSTable writer refuses unsorted input, and tables are written to a `.tmp` file and renamed only after fsync. |
